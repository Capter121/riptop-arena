# NSS Arena 阶段 5A：确定性战斗基础设计

日期：2026-08-09
状态：设计已逐节批准，等待书面规格复核

## 1. 背景

阶段 5 的最终目标是确定性异步好友挑战。当前项目已经具备五层装配、七属性规则、发射、回合行动、QTE、实时碰撞和胜负流程，但影响战果的随机调用仍分散在伤害、AI、碰撞物理、技能和道具生成中，战斗更新也直接消费浏览器每帧的可变 `dt`。

因此，仅保存挑战种子并不能保证不同刷新率或不同 JavaScript 运行环境得到相同结果。阶段 5A 先建立后续挑战持久化、API 和 UI 所依赖的确定性战斗基础。

## 2. 目标

1. 相同模拟版本、种子、装配状态和语义化输入产生字节一致的结果摘要。
2. 将影响战果的随机与视觉随机彻底隔离。
3. 战斗状态固定按 60Hz 推进，渲染、音频和纯视觉动画保持可变帧率。
4. 保持现有装配属性、发射、回合动作、QTE、物理碰撞、技能和胜负流程不变。
5. 为后续异步挑战提供稳定的种子、输入记录、版本和结果摘要契约。

## 3. 非目标

阶段 5A 不包含：

- 挑战数据库迁移或不可变挑战快照。
- 挑战创建、收件箱、详情或结果提交 API。
- VS 界面、应战、分享或回挑战 UI。
- 完整服务端无界面战斗引擎。
- 永久保留所有历史模拟器版本。
- 逐像素或逐帧一致的视觉回放。
- 对现有战斗规则、属性加成或操作方式进行重新平衡。

## 4. 已批准决策

### 4.1 子阶段范围

阶段 5A 合并原总计划任务 5.1 和 5.2：先建立确定性随机服务，再迁移所有影响战果的随机调用。挑战持久化、API 和 UI 作为后续独立子阶段设计与实施。

### 4.2 种子控制权

- 战斗引擎只接受外部传入的种子。
- 本地对战在开局时生成并记录一次种子。
- 未来异步挑战由服务端生成并固化种子，客户端不能重抽。
- 复验必须使用原种子重新创建完整比赛上下文。

### 4.3 随机流结构

根种子稳定派生四条领域流：

- `combat`：伤害、闪避和暴击。
- `ai`：AI 动作、技能、QTE 压力和发射参数。
- `physics`：反射、反冲和影响位置的技能选择。
- `spawn`：影响战果的场内道具生成。

四条流互不消费彼此状态。视觉系统不获得这些流。

### 4.4 时间模型

- 战斗状态固定按 `1 / 60` 秒推进。
- 渲染、网格同步、粒子、镜头、音频和 UI 动画继续使用真实 `dt`。
- 玩家输入记录为语义化动作，不保存墙钟时间。
- 会暂停战斗状态的 Hit-stop 使用固定 tick 计数。

### 4.5 兼容策略

- 初始 `simulationVersion` 固定为 `1`。
- 现有共享 `battleRulesVersion` 继续表示属性与战斗公式版本；`simulationVersion` 单独表示 PRNG、随机消费顺序、固定步进和摘要契约版本。未来挑战必须同时保存两者。
- 两个版本不能在业务源码中多处重复硬编码，必须分别从各自唯一的共享版本入口读取。
- 战斗记录和未来挑战必须携带版本。
- 不支持的版本明确失败，不静默迁移或使用当前规则重算。
- 当前私人项目不要求永久保留所有旧版模拟器；确有需要时再保留指定旧版。

## 5. 架构与数据流

### 5.1 比赛上下文

比赛上下文采用显式依赖注入，不使用全局随机单例：

```ts
type BattleSimulationContext = {
  simulationVersion: 1;
  seed: BattleSeed;
  random: {
    combat: RandomSource;
    ai: RandomSource;
    physics: RandomSource;
    spawn: RandomSource;
  };
};
```

组件职责：

- `Game` 创建、持有并销毁当场比赛上下文，但不实现 PRNG 算法。
- `src/sim/rng.ts` 实现稳定、无依赖的随机源和领域流派生。
- `src/sim/battleSeed.ts` 负责种子生成、验证、规范化、模拟版本和比赛上下文创建。
- 战斗模块只获得自己所属的随机流，不能访问根种子或其他领域流。
- 返回车库、重新开始或开始下一局时必须销毁旧上下文并重置所有状态。

数据流：

```text
外部种子
  -> BattleSimulationContext v1
  -> combat / ai / physics / spawn
  -> 固定 60Hz 战斗状态更新
  -> 规范化结果摘要

战斗状态 -> Three.js 视觉表现
视觉随机 -> Three.js 视觉表现
```

视觉表现只能读取战斗状态，不能通过视觉随机反向修改位置、生命、转速、体力、精神、倾斜或胜负。

## 6. PRNG 契约

### 6.1 公共种子

- 格式为 128 位、小写、32 位十六进制字符串。
- 本地模式使用 `crypto.getRandomValues()` 生成。
- 测试和未来服务端可以直接注入合法种子。
- 非法长度或字符立即返回 `INVALID_BATTLE_SEED`。
- 不自动裁剪、补零、转小写或重新生成。
- 根种子只用于派生，不直接消费随机数。

### 6.2 算法

- 使用固定 32 位整数哈希将根种子派生为领域状态。
- 每条领域流使用稳定、无依赖的 `mulberry32` 序列。
- 所有位运算显式转换为无符号 32 位整数。
- 派生文本固定为：

```text
nss-arena|simulation-v1|<根种子>|<领域名称>
```

- 领域名称只允许 `combat`、`ai`、`physics` 和 `spawn`。
- 不支持运行时动态创建新领域。

### 6.3 随机源 API

```ts
type RandomSource = {
  nextUint32(): number;
  nextFloat(): number;
  nextInt(min: number, maxExclusive: number): number;
};
```

边界：

- `nextUint32()` 返回 `0..4294967295`。
- `nextFloat()` 返回 `[0, 1)`。
- `nextInt()` 返回整数半开区间 `[min, maxExclusive)`。
- 非整数边界或空区间立即失败。

固定测试向量属于 `simulationVersion = 1` 的稳定契约。

## 7. 固定步进契约

### 7.1 步进规则

- 固定时间片为 `1 / 60` 秒。
- 每个渲染帧把主循环提供的真实 `dt` 加入战斗累加器。
- 单个渲染帧最多执行 4 个战斗 tick。
- 未处理完的少量累积时间保留到下一帧，不主动丢弃。
- tick 边界比较使用一个固定且经过测试的极小容差，并在扣除时间片后清理浮点残差，避免等长的 30Hz、60Hz 和 144Hz 序列因累加误差相差一个 tick。
- 继续沿用当前主循环对输入 `dt` 的 33ms 上限，避免页面恢复后一次补算数百帧。
- 新比赛必须把累加器和 tick 编号重置为零。

### 7.2 固定 tick 更新内容

以下状态使用固定时间片：

- 战斗计时和回合计时。
- AI 决策与 AI QTE 增长。
- 碰撞、速度、位置和边界判定。
- 技能效果、转速及体力衰减。
- 倾斜、稳定和属性战斗效果。
- 道具生成、存在时间和拾取判定。
- 胜负规则和会影响战斗的 Hit-stop。

以下内容继续使用真实 `dt`：

- Three.js 网格同步和视觉插值。
- 粒子、烟雾、尾迹和闪电。
- 镜头、Bloom 和竞技场装饰。
- 音频、HUD 和纯 UI 动画。

## 8. 战果随机迁移

### 8.1 `combat`

- 伤害闪避判定。
- 暴击判定。
- 后续新增的直接伤害概率。

`damage.ts` 不再默认回退到 `Math.random()`。结果相关调用必须显式传入 `combat` 随机源。

### 8.2 `ai`

- AI 回合动作和技能选择。
- 旧对峙系统中的 AI 动作和攻击力度。
- AI QTE 初始压力和固定 tick 波动。
- 本地 AI 的发射力度与角度。

AI QTE 每个固定 tick 至多消费一次 `ai` 随机值。

### 8.3 `physics`

- 防御反射返还比例。
- 攻击者反冲比例。
- 幻影分身结束后真实陀螺位置的选择。

### 8.4 `spawn`

- 能恢复转速或体力的场内道具生成角度和半径。

只有实际生成时才消费 `spawn` 流。道具呼吸、旋转和缩放不消费比赛随机数。

### 8.5 继续使用视觉随机

- 火花、烟雾、尾迹和闪电路径。
- 镜头震动偏移。
- Bloom、竞技场装饰和材质纹理噪声。
- 陀螺网格装饰粒子。
- QTE 和发射蓄力的视觉闪电。
- 地面刮痕显示概率。
- 火焰网格抖动。
- 合成音频细微波动。

实时联机继续由 Host 消费比赛随机流并发送裁决结果，Guest 不重复消费 Host 的随机序列。

## 9. 语义化输入记录

阶段 5A 生成最小战斗记录，不提前包含身份、装配快照或纹章：

```ts
type BattleInputLogV1 = {
  simulationVersion: 1;
  seed: BattleSeed;
  launch: {
    playerPower: number;
    playerAngleDeg: number;
    enemyPower: number;
    enemyAngleDeg: number;
  };
  turns: Array<{
    turnIndex: number;
    playerAction: TurnAction;
    enemyAction: TurnAction;
    qteFinal?: {
      playerScore: number;
      enemyScore: number;
    };
  }>;
};
```

规则：

- 发射值按现有合法范围裁切并规范到固定小数位。
- 回合编号从 1 连续递增。
- 只记录最终采用的动作，不记录点击、悬停或取消。
- QTE 只记录最终分数，不记录逐次按键或墙钟时间。
- AI 动作用于战报诊断；复验时必须重新派生并比较，不能直接作为可信输入。
- 装配、纹章、玩家身份、竞技场和挑战规则在后续不可变挑战快照中定义。

## 10. 规范化结果摘要

```ts
type BattleOutcomeSummaryV1 = {
  simulationVersion: 1;
  seed: BattleSeed;
  winner: 'player' | 'enemy';
  kind: BattleResultKind;
  turnCount: number;
  tickCount: number;
  player: FinalTopState;
  enemy: FinalTopState;
};
```

`FinalTopState` 只包含：

- `spin`
- `integrity`
- `stamina`
- `spirit`
- `burst`
- `tilt`
- `alive`

规范化规则：

- 数字统一到三位小数。
- `-0` 统一为 `0`。
- 拒绝 `NaN` 和无穷值。
- 唯一摘要构造函数固定字段插入顺序。
- 该构造函数输出的 `JSON.stringify()` 字符串是字节一致性契约。
- 不保存粒子、镜头、音频、网格旋转或地面刮痕。

内部物理状态不在每个 tick 强制取整，避免不必要地改变战斗手感；只在生成最终摘要时量化。

## 11. 错误处理

以下情况必须在改变战斗状态前失败：

- 种子格式非法：`INVALID_BATTLE_SEED`。
- 模拟版本不支持：`UNSUPPORTED_SIMULATION_VERSION`。
- 回合、动作、技能、发射值或 QTE 分数非法：`INVALID_BATTLE_INPUT`。
- 复验时 AI 派生动作不一致：`AI_REPLAY_MISMATCH`。
- 最终状态包含非有限数字：`INVALID_BATTLE_OUTCOME`。

不自动重抽种子、不跳过损坏回合、不静默替换动作，也不使用当前规则解释未知版本。

## 12. 测试策略

### 12.1 PRNG 契约测试

- 固定种子和四条领域流测试向量。
- 重复创建上下文得到相同序列。
- 不同领域流互不干扰。
- `nextUint32()`、`nextFloat()` 和 `nextInt()` 边界。
- 非法种子、领域和整数区间。
- Node 与浏览器执行相同向量。

### 12.2 固定步进测试

- 30Hz、60Hz 和 144Hz 渲染序列执行相同数量的战斗 tick。
- 未处理余量保留。
- 单帧最多四个 tick。
- 新比赛完全重置。
- Hit-stop 的战斗暂停 tick 数固定。

### 12.3 模块迁移测试

- 伤害、AI、碰撞、技能和道具使用显式注入的领域流。
- 固定随机序列覆盖成功和失败分支。
- 静态守卫结果模块不直接调用 `Math.random()`。
- 视觉模块继续允许视觉随机。

### 12.4 记录和摘要测试

- 非法版本、回合顺序、动作、数值和种子均被拒绝。
- 三位小数、`-0` 和字段顺序正确。
- 相同种子和语义输入重复执行后摘要字符串完全相同。
- 不同种子至少改变一个结果相关字段。

### 12.5 浏览器整场回归

- 两个独立浏览器上下文使用相同种子、装配和自动化输入完成一局。
- 不同渲染帧节奏下最终摘要逐字节一致。
- 发射、回合按钮、QTE、碰撞、属性效果和胜负界面正常。
- 现有实时联机 Host 裁决路径不被破坏。

### 12.6 完整门禁

至少执行：

- 项目单元测试。
- NSS 共享契约测试。
- 构建与类型检查。
- 相关 Playwright 战斗流程。
- 当前完整回归套件。

## 13. 实施顺序

1. 先写失败测试并实现 PRNG 与比赛上下文。
2. 先写失败测试并实现独立固定步进器。
3. 依次迁移 `combat`、`ai`、`physics` 和 `spawn` 随机。
4. 实现语义化输入记录和结果摘要。
5. 完成浏览器整场确定性回归。
6. 执行完整回归并记录限制。

每一步验证通过后再进入下一步，每个稳定步骤独立提交。不得顺便重构视觉、UI、音频、装配、属性或网络协议。

## 14. 成功标准

- 相同 `simulationVersion`、种子、装配状态和语义化输入得到字节一致的结果摘要。
- 30Hz、60Hz 和 144Hz 渲染节奏不会改变执行相同战斗 tick 后的战果。
- 四条结果随机流互不干扰，视觉随机不消费比赛随机状态。
- 结果相关模块不存在隐式 `Math.random()` 回退。
- 现有博弈模式、属性加成、发射、QTE、物理碰撞和胜负流程保持不变。
- 现有测试、构建、契约测试和相关浏览器回归全部通过。

## 15. 风险与限制

- 浏览器后台节流可能让视觉和实际游玩时间变慢，但不应改变执行相同模拟 tick 后的战果。
- JavaScript 浮点运算使用 IEEE-754 双精度；字节一致性通过固定步进、稳定随机和最终摘要量化保证，不要求逐 tick 序列化物理状态。
- 输入记录可用于复验和诊断，但不能独立作为防作弊凭据；后续服务端仍需验证挑战快照和输入。
- 未来修改随机算法、消费顺序、固定步进或结果公式时必须提升 `simulationVersion`，或明确保留旧版实现。
