# 3D 战斗陀螺游戏设计文档

日期：2026-07-04

## 目标

构建一个类似 `ripcore.netlify.app` 的单机 3D 战斗陀螺网页游戏原型，重点验证以下几点：

- 3D 竞技场中的陀螺对战是否足够好玩
- 发射、碰撞、追击、出界、爆裂这套循环是否清晰且有爽感
- 轻量 3 段式改装是否能提供足够明显的策略差异

第一版目标是做出可玩的浏览器原型，而不是完整商业化产品。

## 产品范围

第一版定位为单机可玩版，明确不做联网对战。

必须包含：

- 1 个 3D 竞技场
- 主菜单
- 车库改装页面
- 对战 HUD
- 结算页面
- 玩家可操作陀螺 1 个
- AI 对手系统 1 套，至少支持 3 套敌方配置
- 发射蓄力和方向控制
- 3 种胜利方式：`ring out`、`spin finish`、`burst finish`
- 3 段式改装：`attackRing`、`core`、`driver`
- 每段 3 个部件
- 基础视觉表现：碰撞火花、拖尾、爆裂、简单慢镜头

明确不做：

- 在线多人
- 剧情模式
- 大量关卡或地图
- 重资产高精度模型
- 复杂经济系统
- 排行榜、账号、云存档

## 技术方向

推荐方案：`Three.js + TypeScript + 自定义轻量物理`

原因：

- 该项目核心是手感，不是通用物理准确性
- 陀螺对战需要大量“好玩优先”的假物理调参
- 自定义轻量物理更适合快速实现碰撞冲量、边缘弹回、失稳、爆裂等玩法逻辑

不采用 `Three.js + Rapier` 作为第一版主路线，原因是它会让后续大量手感覆写更复杂。也不采用纯演出驱动的伪物理路线，因为第一版仍然需要真实可玩的碰撞循环。

## 核心玩法循环

玩家进入主菜单后，进入车库选择改装，随后开始对战。

基础循环如下：

1. 在车库中选择 3 段式配置
2. 进入竞技场
3. 玩家与 AI 完成发射
4. 陀螺对战直到出现出界、停转或爆裂
5. 进入结算
6. 选择再来一局或返回车库

单局时长目标控制在 20 到 45 秒，保证节奏紧凑。

## 视觉方向

采用类似 `ripcore` 的 3D 竞技场表现，但第一版使用简化模型，优先把开发时间投入到：

- 镜头运动
- 速度感
- 碰撞反馈
- 结算演出

视觉策略：

- 模型可以简化，但轮廓必须可辨认
- 场地采用碗状圆形竞技场
- 中心区域稳定，边缘危险
- UI 尽量压缩，避免遮挡对战读图

## 游戏系统设计

### ArenaSystem

职责：

- 创建 3D 竞技场
- 管理边界和危险区域
- 负责出界判定
- 提供地面摩擦和边缘行为参数

第一版采用单一圆形 arena。边缘区域应当明显更危险，以便鼓励高风险高收益的碰撞。

### TopSystem

职责：

- 管理每个陀螺的运行状态
- 管理战斗参数和实时状态
- 维护可视对象与逻辑对象的关联

每个陀螺至少包含以下状态：

- `position`
- `velocity`
- `spin`
- `stamina`
- `integrity`
- `tilt`
- `alive`

说明：

- `spin` 决定转速和部分攻击势能
- `stamina` 决定停转趋势
- `integrity` 决定爆裂承伤能力
- `tilt` 决定失稳感和接近停转的表现

### BattlePhysicsSystem

职责：

- 推进陀螺运动
- 计算摩擦和减速
- 处理相撞冲量
- 处理边缘反弹和危险区效果
- 触发擦碰、重击、爆裂相关事件

设计原则：

- 追求可读和有爽感的物理
- 不追求完全真实
- 优先保证不同配装碰撞结果差异明显

该系统不直接负责 UI 和结算文案，只产出状态与事件。

### LaunchSystem

职责：

- 处理玩家蓄力与方向输入
- 生成初始发射参数
- 驱动 AI 发射行为

玩家输入至少包括：

- 按住蓄力
- 选择方向
- 确定旋向

AI 与玩家共用同一发射入口，只是输入参数来源不同。

### RuleSystem

职责：

- 管理回合和结算状态
- 判定胜负
- 触发慢镜头和结算文案

支持三种结算：

- `ring out`
- `spin finish`
- `burst finish`

当出现结算条件时，系统负责冻结或减速比赛状态，播放结算表现，然后进入结果页。

### BuildSystem

职责：

- 管理 3 段式改装
- 汇总部件属性
- 生成统一战斗参数

部件结构：

- `attackRing`
- `core`
- `driver`

## 改装与数值模型

第一版每段提供 3 个部件，总共 9 个。

建议部件风格如下：

### attackRing

- `Slash`：高攻击，低防御
- `Round`：均衡
- `Bulwark`：低攻击，高抗性

### core

- `Light`：机动强，耐久低
- `Balanced`：均衡
- `Heavy`：更稳，更抗撞

### driver

- `Rush`：移动快，耗转高
- `Grip`：稳定，易控
- `Drift`：机动强，但更难控

最终统一映射到 5 个战斗参数：

- `attack`
- `defense`
- `stamina`
- `mobility`
- `burstResist`

参数作用：

- `attack`：影响碰撞伤害和击退
- `defense`：影响承受冲量后的损失
- `stamina`：影响停转衰减
- `mobility`：影响推进、转向、冲刺
- `burstResist`：影响爆裂槽承伤能力

原则：

- 玩家理解的是部件风格
- 系统调参依据的是统一参数层

这样后续增加新部件时，不需要改动物理主逻辑。

## AI 设计

第一版 AI 不追求复杂决策，只需要支撑可玩性验证。

至少提供 3 套敌人模板：

- 激进型：偏攻击与高速追击
- 平衡型：综合能力较平均
- 坦克型：偏防御与耐久

AI 需要具备以下能力：

- 合法发射
- 基础追击或走位
- 在边缘附近有一定回避倾向

## UI 设计

第一版 UI 包含以下部分：

### 主菜单

- 开始对战
- 进入车库
- 返回标题或重新开始

### 车库

- 选择三段配件
- 即时显示总属性倾向
- 提供开始对战入口

### 对战 HUD

- 玩家与敌方状态条
- 转速或耐力表现
- 爆裂相关提示
- 简洁结算提示

### 结算页

- 胜负结果
- 结算类型
- 再来一局
- 返回车库

移动端要求：

- 默认支持横屏
- 关键按钮具备足够触控区域
- HUD 保留安全区边距

## 表现层设计

第一版必须具备以下反馈：

- 碰撞火花
- 碰撞或滑行拖尾
- 爆裂瞬间表现
- 结算慢镜头

表现触发应通过事件驱动，避免在物理系统内部直接拼接特效对象。

## 项目结构

建议目录结构如下：

```text
src/
  main.ts
  app/
    game.ts
    loop.ts
    config.ts
  scene/
    arena.ts
    lighting.ts
    cameraRig.ts
  gameplay/
    top.ts
    build.ts
    launch.ts
    battlePhysics.ts
    rules.ts
    ai.ts
  ui/
    hud.ts
    menus.ts
    garage.ts
    results.ts
  data/
    parts.ts
    enemies.ts
    tuning.ts
  fx/
    sparks.ts
    trails.ts
    burst.ts
  utils/
    math.ts
    events.ts
    state.ts
```

边界原则：

- `scene` 管画面和镜头
- `gameplay` 管玩法规则
- `ui` 管界面
- `data` 管配表
- `fx` 管表现

避免把主要玩法逻辑写进单个超大文件。

## 验收标准

第一版完成时，需满足以下标准：

1. 玩家首次进入后 1 分钟内能开始一局对战
2. 发射、碰撞、追击、出界的读图清晰
3. 不同配件组合带来的差异明显可感知
4. 三种结算都能稳定触发
5. 单局流程完整，无卡死或必须刷新页面的问题
6. 桌面端与手机横屏都可正常游玩
7. 画面不是空白 canvas
8. HUD 不遮挡关键视野
9. 触控按钮可正常点击

## 实现顺序

后续实现建议按以下顺序推进：

1. 搭建 `Vite + TypeScript + Three.js`
2. 建立 arena、camera、lighting、基础 loop
3. 建立陀螺实体与参数结构
4. 实现发射系统
5. 实现轻量物理与碰撞
6. 实现三种胜负判定
7. 实现 AI
8. 实现 HUD、菜单和结算
9. 实现改装系统
10. 加入特效和打磨
11. 使用 QA 流程完成桌面端、移动端、构建与发布检查

## 测试策略

测试重点如下：

- 单局从进入到结算的完整闭环
- 三种胜负方式分别可复现
- 不同 build 对战时的差异性验证
- 桌面端键鼠输入
- 移动端横屏触控输入
- 构建产物在预览环境中的可用性

后续进入 QA 与发布阶段时，使用 `threejs-qa-release` 技能执行：

- 桌面端与移动端截图检查
- 非空白 canvas 验证
- HUD 文本和安全区检查
- 构建、预览和发布检查

## 风险与边界

主要风险：

- 第一版若过度追求真实物理，可能损失开发速度和可玩性
- 若过早扩展多人，会显著拖慢项目推进
- 若过早投入高精度模型，会挤占玩法调试时间

因此本项目第一版坚持以下边界：

- 先把手感做好
- 先把单局闭环做完整
- 先让改装差异足够明显
- 不在第一版引入联网复杂度

## 推荐结论

推荐立刻进入实现计划阶段，围绕单机 3D 战斗陀螺原型推进。

该方向适合作为项目第一阶段，因为它：

- 题材与玩法匹配度高
- 可在较短周期内验证乐趣
- 保留了后续扩展到更多内容或多人模式的空间
