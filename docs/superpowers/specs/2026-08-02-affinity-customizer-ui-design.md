# NSS 属性装配界面设计

日期：2026-08-02
状态：已批准，待实施

## 1. 背景与目标

上一阶段已经为五层 NSS 零件组合加入可附加属性、确定性属性结算、本地存储迁移以及撤销/重做能力。本阶段只为现有 3D 定制器增加玩家可见的属性装配入口和共鸣结果，不改变零件模型、物理属性或竞技场战斗流程。

目标是让玩家在现有五层装配流程中快速完成以下操作：

- 查看每个候选零件当前附加的属性。
- 为当前零件从风、火、水、木、土、光、暗中选择一个属性。
- 立即看懂五层属性数量、主属性、共鸣加成、克制对象和弱点。
- 在桌面浏览器与手机浏览器中完成同一套操作。

## 2. 成功标准

- 现有五个零件分类和零件横向选择流程保持不变。
- 每张零件卡使用图形、中文名称和颜色共同表达当前属性，不能只依赖颜色。
- 属性选择只更新当前分类的附加属性，不更换零件，不触发 3D 模型重新加载。
- 属性结果完全来自现有 `resolveAffinityProfile` 结算结果，界面不复制业务规则。
- 属性变化进入现有撤销、重做和本地保存流程。
- 手机端不遮挡 3D 视图、五层分类或零件选择，属性按钮触控目标至少约 44 CSS 像素。
- 新增组件单元测试、定制器端到端测试、类型检查和生产构建全部通过。

## 3. 已批准的布局

采用“当前零件内联选择”布局。

### 3.1 零件卡

现有零件卡保留零件缩写与名称，并增加紧凑属性徽章。徽章包含一个稳定的属性图形标记、完整中文名称和对应强调色。例如火属性显示火焰标记和“火”，光属性显示光芒标记和“光”。

未选中的候选零件同样显示该层当前附加属性，因为 A2 模型中属性属于装配槽位，而不是固定属于某一零件。切换同一分类的候选零件不会擅自改变该层属性。

### 3.2 属性选择条

零件横向列表下方显示七个属性按钮。选择条只作用于当前 `selectedFamily`，切换分类后立即显示该层当前属性。

按钮必须具备默认、悬停、键盘聚焦、按下和已选择状态。已选择按钮使用 `aria-pressed="true"`；控件组拥有明确的中文无障碍标签。

桌面端在可用宽度内排列七个按钮。手机端保持每个按钮至少约 44 CSS 像素宽高，并允许选择条横向滚动，不把七个按钮压缩成难以点击的小目标。

### 3.3 属性共鸣面板

共鸣面板位于零件与属性选择区下方、现有底部工具区上方，占据独立横向区域。它不悬浮在 3D 视图上，也不覆盖五层分类。

面板显示：

- 七种属性的数量；数量为零的属性仍保留紧凑标记，以便玩家理解完整规则集合。
- 当前主属性。
- 当前共鸣类型与数值；无共鸣时明确显示“未形成共鸣”。
- 主属性克制的属性和受到克制的属性。

手机端面板改为单列摘要，保持字段顺序不变。数值变化可以使用短暂、低强度的颜色或描边反馈，但不加入持续动画，不干扰配装。

## 4. 组件边界

### 4.1 `AffinityBadge`

纯展示组件。输入一个属性值和可选的紧凑模式，输出属性图形、中文名称、主题色和可访问文本。它不读取全局状态，也不计算属性规则。

### 4.2 `AffinityPanel`

负责属性选择条和共鸣摘要。输入当前分类、五层属性映射和已经计算好的属性档案；通过回调提交“为某分类设置属性”的意图。它不直接修改 3D 场景或战斗状态。

### 4.3 `App`

继续负责界面编排。它把现有状态中的 `selectedFamily`、`affinities`、`affinityProfile` 和 `setAffinity` 传给属性组件，并在零件卡中放置 `AffinityBadge`。

不新增第二套属性状态，也不为本阶段引入新的状态管理或配置层。

## 5. 数据流

1. 玩家选择一个零件分类。
2. `App` 从 `state.affinities[selectedFamily]` 取得当前层属性。
3. 玩家点击七属性选择条中的一个按钮。
4. `AffinityPanel` 调用 `setAffinity(selectedFamily, affinity)`。
5. 现有 store 更新属性、重新调用 `resolveAffinityProfile` 并记录历史；玩家执行现有“保存本地”动作时，当前属性随组合一起持久化。
6. 徽章和共鸣面板从更新后的状态重新渲染。
7. 由于零件组合没有改变，3D 模型选择和加载流程不运行。

## 6. 属性表现规则

界面只呈现已经批准的规则，不自行推导新规则：

- 自然循环：风克土、土克水、水克火、火克木、木克风。
- 光与暗互相克制。
- 三、四、五个相同属性分别显示进攻共鸣的元素份额加成 `+6%`、`+10%`、`+15%`。
- `2-2-1`、`2-1-1-1`、五属性全不同分别显示对应防御与稳定加成。
- 主属性平票继续使用已经实现的核心优先与固定顺序规则。

所有文案数值来自 `affinityProfile`，避免界面规则与竞技场规则漂移。

## 7. 文案与现有文件处理

`battle-top-designer/web-customizer/src/i18n/zhCN.ts` 是工作区中已有但尚未纳入 Git、且当前应用没有导入的用户文件。本阶段不覆盖、不移动、不提交该文件。

本阶段所需的七个属性名称和共鸣短文案集中在新属性展示模块中。统一接入全局中文资源属于后续独立任务，避免本阶段扩大改动范围或误改用户文件。

## 8. 错误与边界处理

- 无效或旧版持久化数据继续由现有 store 迁移与安全回退处理，UI 不增加第二套校验。
- 若共鸣档案不存在可展示的加成，面板显示“未形成共鸣”，不显示空白区域。
- 属性选择在模型加载期间仍可更新，因为它不依赖模型加载；零件选择原有禁用与加载行为不变。
- 快速连续选择以 store 中最后一次有效属性为准，React 状态更新不引入额外队列。
- `prefers-reduced-motion` 下禁用属性反馈动画。

## 9. 验证设计

### 9.1 组件单元测试

- `AffinityBadge` 对七个属性输出正确的图形、中文名和可访问文本。
- `AffinityPanel` 显示七种数量、主属性、进攻共鸣、调和共鸣以及无共鸣状态。
- 点击属性按钮提交正确的分类和属性，并标记唯一已选择按钮。

### 9.2 状态与回归测试

- 属性变化更新档案但不改变五层零件组合。
- 属性变化可撤销、重做并通过现有本地存储恢复。
- 原有零件切换、分享、导入导出和进入竞技场流程保持通过。

### 9.3 浏览器验证

- 桌面与手机视口均验证零件分类、零件列表、属性选择条和共鸣面板无覆盖或裁切。
- 手机端验证属性按钮触控尺寸与横向滚动可达性。
- 切换属性前后监测加载状态，确认不出现新的模型加载周期。
- 检查键盘操作、焦点可见性、`aria-pressed` 与浏览器控制台错误。

## 10. 非目标

- 不修改竞技场战斗算法或战斗模式。
- 不为属性加入新的 3D 材质、粒子或音效。
- 不修改零件物理属性或概念属性计算。
- 不改造整个定制器的国际化架构。
- 不加入服务端身份、邀请码、图片编辑或 AI 生成功能。
- 不重构现有 `App` 中与属性界面无关的功能。

## 11. 实施顺序

1. 先编写属性徽章和共鸣面板的失败测试。
2. 实现纯展示组件与属性元数据。
3. 在现有零件卡和底部布局中接入组件。
4. 增加响应式样式和无障碍状态。
5. 增加桌面、手机端端到端测试并执行完整验证。
