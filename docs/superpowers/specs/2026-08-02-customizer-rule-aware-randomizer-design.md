# 定制器规则预设与受约束随机装配设计

日期：2026-08-02
状态：已批准，待实施计划

## 1. 背景

定制器已有五层零件和附加属性编辑、属性共鸣、数值差异预览、构筑流派解释以及无约束“随机组合”。当前随机函数只随机零件，并把附加属性恢复为默认值；它不知道比赛规则，也不能解释当前装配为什么不符合某个规则。

本阶段是总体路线任务 2.4B。它在不改变战斗模式、流派评分和属性加成的前提下，增加固定规则预设、结构化违规解释和可信的受约束随机装配。

## 2. 目标

1. 提供四个不可编辑倍率的固定规则预设。
2. 对当前“零件 + 五层附加属性”装配给出完整、确定性的合法性结果。
3. 让随机装配在规则有解时必定返回合法结果。
4. 让随机零件和属性成为一次可撤销操作。
5. 在桌面和移动端的现有“组合快捷工具”内紧凑呈现规则状态。

## 3. 成功标准

- 四个规则预设的定义固定且有正反测试。
- 重量上限使用零件 `physics.weight` 原始和进行判定，恰好 `2.10` 合法。
- 元素专精支持风、火、水、木、土、光、暗七种属性，目标属性至少三件。
- 基础零件杯能识别所有被禁零件。
- 同一装配的全部违规原因一次返回，顺序稳定。
- 受约束随机器不依赖有限次数重试；只要存在合法集合就必定成功。
- 随机后一次撤销同时恢复零件和五层属性。
- 手动违规仍可继续编辑，不改变原有进入竞技场能力。
- 规则不进入战斗乘区，不修改构筑流派评分。

## 4. 本阶段范围

### 4.1 纳入范围

- 禁用零件。
- 总重量上限。
- 指定属性最低件数。
- 固定预设选择。
- 结构化违规提示。
- 受约束随机零件及属性。
- 原子撤销和重做。

### 4.2 延期范围

当前数据尚未提供稀有度、解锁状态、套装归属和竞技场选择，因此本阶段不实现：

- 稀有度上限。
- 只从已解锁零件随机。
- 禁止重复套装。
- 公平基础属性模式。
- 固定竞技场。
- 自定义规则编辑器。
- 规则存档、分享载荷或服务端比赛规则。

延期项目不能通过占位稀有度、假解锁状态或虚拟套装数据模拟。本阶段视当前目录中的全部零件为可用零件。

## 5. 固定规则预设

### 5.1 自由组装 `FREE`

无额外限制。

### 5.2 轻量竞技 `LIGHTWEIGHT`

五件零件的 `physics.weight` 总和不得超过 `2.10`。显示值保留两位小数，但合法性使用未格式化的原始数值计算。

### 5.3 元素专精 `ELEMENT_SPECIALIST`

用户从七种现有属性中选择目标：`WIND`、`FIRE`、`WATER`、`WOOD`、`EARTH`、`LIGHT`、`DARK`。五层附加属性中目标属性至少出现三次。最低件数固定为三，不提供数值编辑。

### 5.4 基础零件杯 `BASIC_PARTS_CUP`

禁用以下零件：

- `blade_storm_fang`（Storm Fang）
- `blade_iron_bastion`（Iron Bastion）
- `assist_heavy`（Heavy Assist）

## 6. 共享规则模块

新增 `battle-top-designer/shared/nss/build-rules.ts`。该文件只负责规则数据、校验、合法候选过滤和随机结果，不依赖 React 或 Zustand。

### 6.1 核心类型

- `BuildRulePresetId`：四个固定预设标识。
- `BuildRuleSelection`：预设标识；元素专精额外包含目标属性。
- `RuleBuild`：完整的 `combination` 和 `affinities`。
- `BuildRuleViolation`：结构化违规项。
- `RandomBuildResult`：成功或失败判别联合。

违规项至少包含：

- `DISABLED_PART`：零件 ID、槽位和显示名。
- `WEIGHT_LIMIT`：实际重量、上限和超出值。
- `AFFINITY_MINIMUM`：目标属性、实际件数、最低件数和缺少件数。

违规顺序固定为禁用零件（按 core、blade、assist、gear、tip 槽位顺序）、重量、属性要求，保证 UI 和测试稳定。

### 6.2 纯函数边界

1. `validateBuild(build, selection)`：返回所有违规项，不提前停止。
2. `eligibleParts(family, selection)`：返回该槽位允许参与随机的当前目录零件。
3. `randomBuild(selection, random)`：返回 `{ ok: true, build }` 或 `{ ok: false, violations }`。

所有函数不得修改输入对象。随机函数通过参数注入，生产环境默认使用 `Math.random`，测试使用固定序列。

## 7. 随机算法

### 7.1 零件

1. 使用现有目录枚举全部 288 种零件组合。
2. 使用与 UI 相同的 `validateBuild` 规则过滤合法组合。
3. 从合法集合中选择一个索引。

零件规则和属性规则相互独立，因此不创建 288 与所有属性组合的笛卡尔积。

### 7.2 附加属性

- `FREE`、`LIGHTWEIGHT`、`BASIC_PARTS_CUP`：使用所选核心对应的现有默认五层属性。
- `ELEMENT_SPECIALIST`：枚举 `7⁵` 个五层属性组合，过滤目标属性出现次数不少于三的候选，再随机选择一个。

### 7.3 最终保障

生成完整 `RuleBuild` 后再次调用 `validateBuild`。成功结果必须无违规。若合法集合为空或最终保障失败，返回失败结果，不返回部分装配。

该设计不使用“最多尝试 N 次”的随机重试，因此不会发生有解但运气不好而失败。

## 8. 定制器状态和历史

- 当前规则选择属于定制器会话状态，不写入本地装配存档、分享链接或 Arena 载荷。
- 切换规则不修改装配，不进入撤销历史。
- 手动换件或改属性后立即重新校验，但违规不阻止继续编辑。
- 新增原子替换完整装配的 store 动作，使受约束随机一次写入零件和属性。
- 随机结果相对当前装配确有变化时，只增加一条历史记录。
- 撤销和重做恢复完整的零件与属性快照。
- 随机失败时装配、属性、流派、历史、加载状态和本地存档均保持不变。

## 9. 界面设计

采用已批准的布局 A：规则控制内嵌现有“组合快捷工具”。

- 标题下显示四个固定预设选项。
- 元素专精被选中时显示七属性选择；默认目标可使用 `FIRE`，但切换到该预设不自动修改装配。
- 原“随机组合”按钮改为“按规则随机”。
- 合法状态使用简短绿色文案，例如“符合轻量竞技 · 2.03 / 2.10”。
- 违规状态使用琥珀色列表，显示可行动原因和具体差值。
- 规则提示不禁用“进入竞技场”。本阶段规则是本地装配辅助，不冒充服务端强制比赛规则。
- 移动端纵向排列，不增加弹窗、抽屉或浮动控件。

该功能不新增动画，不改变现有 3D 场景、焦点切换或零件预览交互。

## 10. 数据流

1. 用户选择规则预设或元素目标。
2. UI 将当前 `combination`、`affinities` 和规则选择传给共享校验器。
3. UI 渲染合法摘要或完整违规列表。
4. 用户点击“按规则随机”。
5. 共享随机器生成完整装配，并由同一校验器复核。
6. 成功时 store 原子替换装配，现有属性、共鸣、差异预览和流派计算自动派生更新。
7. 失败时 UI 显示失败原因，store 不发生写入。

## 11. 错误处理

- 未知预设或无效属性属于编程错误，由共享模块明确拒绝，不静默回退为自由规则。
- 无合法零件组合返回可显示的失败结果。
- 随机成功后的防御性复核若发现违规，转为失败结果。
- UI 不把规则失败写入全局模型加载错误，避免遮蔽现有 3D 加载状态。
- 当前装配可以同时显示多个违规原因，便于玩家一次修正。

## 12. 测试策略

### 12.1 共享单元测试

- 四个固定预设定义。
- 重量 `2.10` 边界及超重反例。
- 七种属性各自的三件合法、两件违规样例。
- 三个禁用零件的独立反例。
- 多重违规一次完整返回且顺序稳定。
- `eligibleParts` 不返回禁用零件。
- 随机值 `0`、接近 `1` 和固定序列均返回合法结果。
- 多组固定随机序列不产生违规结果。
- 输入不可变和相同随机序列可复现。
- 人工无解规则路径返回失败，不返回非法装配。

### 12.2 Store 单元测试

- 完整装配替换只产生一条历史。
- 一次撤销和重做同时恢复零件与属性。
- 相同装配不产生空历史记录。
- 随机失败不改变任何 store 状态。

### 12.3 组件测试

- 四个预设可选择，参数不可任意编辑。
- 元素专精显示全部七种属性。
- 合法摘要、单一违规和多重违规正确呈现。
- 违规不会禁用进入竞技场。

### 12.4 端到端测试

- 桌面端切换轻量竞技并观察合法或超重状态。
- 火元素专精随机结果至少有三层火属性。
- 基础零件杯随机结果不包含三个禁用零件。
- 随机后一次撤销完整恢复零件和属性。
- 412px 移动视口规则区无横向滚动、裁切或控件重叠。

## 13. 风险与限制

- 规则仅在当前浏览器会话生效，刷新后恢复默认自由组装。
- 本阶段不向 Arena 或服务端传递规则，因此不能用于防作弊或强制比赛准入。
- 当前零件和属性规模很小，枚举成本可控；若未来目录显著扩大，应先用性能测试证明存在瓶颈，再替换算法。
- 稀有度、解锁、套装、公平模式和竞技场规则必须等待真实数据模型，不能在本阶段推测实现。

## 14. 明确不变项

- 原有战斗操作和博弈模式不变。
- 属性克制、共鸣数值和七属性集合不变。
- 构筑流派不获得战斗加成，评分公式不变。
- 现有存档和分享 schema 不变。
- Arena 不读取本阶段规则预设。
