# Nova Spin System × RIPTOP Arena 完整扩展设计

日期：2026-08-01
状态：已批准，等待用户审阅书面规格
范围：方案 A（核心系统）、方案 B（单人内容）、方案 C（创作社区）

## 1. 产品目标

本项目面向受邀朋友，通过公网部署，但不开放公共注册。玩家通过邀请码进入，首次填写昵称，浏览器生成并保存本地设备身份。

完整产品循环为：

1. 获得或解锁零件。
2. 在 NSS 定制器中完成五层装配。
3. 查看基础属性、七属性分布、共鸣和构筑流派。
4. 参加战役、生存、异步挑战或实时好友战斗。
5. 获得金币、零件和外观奖励。
6. 制作并应用个人纹章。
7. 发布配装、纹章和战绩。
8. 朋友复制配装、收藏作品或发起挑战。

核心目标不是替换现有战斗，而是在现有战斗上增加装配策略、单人目标、好友传播和玩家身份。

## 2. 已确认的产品约束

### 2.1 保持不变

- Three.js 竞技场和现有物理表现。
- 五层 NSS 装配方式。
- 发射倒计时和发射 QTE。
- 回合行动种类、技能消耗和反击关系。
- 碰撞、格挡、暴击、出界和爆裂流程。
- 现有金币、商店、工坊、黑市和零件强化。
- 现有 WebSocket 实时匹配基础。

### 2.2 需要修改

- NSS 配装采用“零件模型 + 可附加属性”，属性不固化到模型目录。
- 配装计算增加元素共鸣、协调和流派解释。
- 主动攻击伤害拆分为物理与元素两部分。
- 现有生存入口扩展为完整波次玩法。
- 配装分享增加版本与挑战载荷。
- WebSocket 连接增加邀请身份。
- 进度由纯本地存储扩展为服务器持久化。

### 2.3 明确不做

- Steam、Electron、Tauri 或 Steamworks。
- 密码、邮箱验证和找回密码。
- 公共开放注册。
- 评论、私信、关注和好友申请。
- 每日签到、体力、限时商店和多货币运营。
- 多服务器扩容。
- 第一版直接接入 AI 图像生成。

### 2.4 A2 属性装配约束

- 五层零件都可以独立附加风、火、水、木、土、光、暗中的任意一种属性，因此七种属性都能组成五件同属性共鸣。
- 模型组合 ID 只描述五层模型，继续保留现有 288 个编号；属性选择作为 V2 配装中的独立字段保存。
- 机械接口 ID 继续使用 `NSS-V1`，配装 `schemaVersion` 升级为 2。
- V1 旧配装迁移时，`core_solar_wolf` 默认为光，`core_void_falcon` 默认为暗；刃环、辅助环、齿轮和底尖依次默认为风、火、水、土。
- 木属性不用于旧配装默认迁移，但仍可自由附加到任意一层。

## 3. 总体架构

采用模块化 Node 单体：

- Vite/Three.js：RIPTOP Arena。
- React/R3F：NSS 定制器和纹章工坊。
- Node HTTP：REST API、静态文件和上传资源。
- 现有 Node WebSocket：实时匹配和房间通信。
- SQLite：身份、构筑、挑战、进度、成绩和作品元数据。
- 服务器本地目录：标准化后的纹章 WebP。

### 3.1 前端边界

NSS 定制器负责：

- 五层部件装配。
- 属性差异和来源解释。
- 七属性分布与共鸣。
- 构筑流派。
- 规则校验和受约束随机配装。
- 纹章制作、预览和应用。

RIPTOP Arena 负责：

- 快速战斗。
- 实时好友战斗。
- 异步挑战。
- 八名对手战役。
- 生存模式。
- 战斗结算与战报。

统一门户只负责：

- 邀请验证与昵称。
- 玩家摘要、金币和当前配装。
- 模式入口。
- 未处理挑战和最近朋友动态。

不把两个前端强行重写成一个 React 应用。

### 3.2 服务端模块


各模块只承担一个领域职责；不拆微服务，不引入通用 GraphQL 或大型后端框架。

## 4. 邀请身份和数据持久化

### 4.1 身份流程

1. 玩家打开 `https://host/join?invite=<code>`。
2. 服务端验证邀请码状态和使用次数。
3. 玩家填写昵称。
4. 服务端创建 `playerId` 和安全随机设备令牌。
5. 浏览器保存 `playerId`、设备令牌和昵称。
6. 服务端只保存令牌哈希。
7. HTTP 和 WebSocket 请求使用同一身份凭据。

邀请码仅用于首次进入。停用邀请码不影响已创建玩家。清除浏览器数据后默认无法恢复原身份。

### 4.2 SQLite 表

| 表 | 作用 |
|---|---|
| `invites` | 邀请码、状态、使用上限和次数 |
| `players` | 昵称、设备令牌哈希和创建时间 |
| `builds` | NSS 构筑快照和目录版本 |
| `challenges` | 异步挑战输入、状态和结果 |
| `campaign_progress` | 对手星级、最佳结果和奖励状态 |
| `scores` | 生存、赛事和公平战斗成绩 |
| `emblems` | 纹章图片路径和编辑参数 |
| `favorites` | 玩家收藏作品 |
| `activity` | 高价值朋友动态 |

## 5. 七属性装配系统

### 5.1 属性定义

五层零件使用七种基础亲和：

```text
WIND、FIRE、WATER、WOOD、EARTH、LIGHT、DARK
```

现有属性迁移：

- `ROCK → EARTH`
- `LIGHTNING → WIND`
- `DIVINE → LIGHT`

迁移只处理保存层的 NSS 属性，并提供独立的旧实例物品转换函数。现有运行时 `LIGHTNING`、`DIVINE` 战斗判定、商店生成和视觉效果暂时保留，后续再把技能/视觉标签与基础装配属性分离；它们不扩大基础相克表。

### 5.2 相克关系

自然属性闭环：

```text
风克土 → 土克水 → 水克火 → 火克木 → 木克风
```

光暗互相克制，对自然五属性中立。光暗对局属于双方元素进攻都增强的高风险对局。

### 5.3 主属性

系统统计五层属性数量。数量最多者为主属性；若并列且战魂核心属性属于并列候选，由核心裁定；若核心不属于并列候选，则按风、火、水、木、土、光、暗的固定顺序裁定。计算不使用随机数。

### 5.4 纯属性进攻共鸣

| 同属性数量 | 元素进攻强度 |
|---:|---:|
| 1–2 | 无加成 |
| 3 | +6% |
| 4 | +10% |
| 5 | +15% |

共鸣只增强元素伤害部分，不直接乘算全部最终伤害。

### 5.5 混合属性协调共鸣

协调共鸣仅在没有任何属性达到三件时触发：

| 分布 | 防御 | 稳定性 |
|---|---:|---:|
| 2-2-1 | +5% | +6% |
| 2-1-1-1 | +7% | +8% |
| 1-1-1-1-1 | +9% | +10% |

稳定性作用于自然转速消耗、碰撞倾斜增长和低转速失控。进攻共鸣与协调共鸣互斥。

### 5.6 伤害接入

只有主动攻击和攻击型反击携带元素伤害：

```text
有效攻击伤害 = 80% 物理 + 20% 元素
```

元素部分依次应用：

1. 纯属性共鸣。
2. 属性克制。
3. 光暗极化。

推荐克制倍率：优势 `1.25`，劣势 `0.8`。由于只作用于 20% 元素部分，最终总伤害影响约为 `+5% / -4%`。

自然转速衰减、墙壁碰撞、场地危险和非攻击状态伤害保持中立物理伤害。

### 5.7 技能与装配属性

技能形式不决定攻击属性：

- 技能决定等级、精神消耗、行为效果和视觉。
- 陀螺主属性决定元素伤害属性。

例如火属性陀螺使用风刃，仍造成火属性元素伤害；风刃的等级、消耗、动作和原有效果不变。

## 6. 共享元素核心

共享 NSS 目录新增：

```text
battle-top-designer/shared/nss/
  affinity.ts
  affinity-rules.json
```

`affinity-rules.json` 保存规则版本、属性、克制、共鸣阈值和倍率。`affinity.ts` 实现无 DOM、无 Three.js、无存储、无随机数的纯函数。

核心输出：

```ts
interface AffinityProfile {
  rulesVersion: number;
  primary: PartAffinity;
  counts: Record<PartAffinity, number>;
  resonance: OffenseResonance | HarmonyResonance | NoResonance;
  modifiers: {
    elementalPower: number;
    defenseMultiplier: number;
    spinDrainMultiplier: number;
    tiltGrowthMultiplier: number;
  };
}
```

定制器和 Arena 使用同一实现。服务端只验证零件、目录版本和规则版本，不接受客户端提交的共鸣数值。

## 7. 方案 A：核心系统

### 7.1 属性差异

悬停或替换零件时显示基础数值、属性数量、共鸣和流派变化，并显示数值来源。

### 7.2 构筑流派

第一版使用六种解释标签：强袭、堡垒、耐久、反击、爆裂、均衡。标签不提供额外战斗加成。

### 7.3 规则预设

支持禁用零件、重量上限、稀有度上限、属性要求、禁止重复套装、公平基础属性和固定竞技场。玩家选择预设，不开放任意倍率编辑。

### 7.4 异步挑战

挑战保存：挑战者、不可变构筑快照、纹章、竞技场、规则、发射结果、随机种子和短挑战语。

流程：收到挑战、VS 入场、选择配装、发射、确定性战斗、提交结果、回挑战。

挑战只保存零件 ID、五层属性选择和版本，不保存可伪造的最终共鸣值。

### 7.5 公平规则

默认“公平竞技”使用零件基础属性，忽略永久整机和零件强化，计入公平战绩。

“全力乱斗”使用真实强化和稀有部件，不计公平排行榜。单人战役和生存允许使用成长后的真实配置。

## 8. 方案 B：单人内容

### 8.1 八名对手战役

八名对手依次教授基础战斗、属性克制、被克制、纯属性共鸣、协调共鸣、反击、光暗极化和综合构筑。

每名对手由数据定义：昵称、纹章、属性主题、两至三套配装、AI 权重、竞技场、规则、三星目标、奖励和台词。不得为每个对手复制战斗代码。

### 8.2 三星目标

每关包含胜利目标、特殊战斗目标和不同构筑通关目标。星级解锁后续对手、纹章边框和非数值奖励。

### 8.3 生存模式

生存循环：波次、普通/精英敌人、波次后三选一、每五波 BOSS、风险倍率和最终结算。

局内奖励仅本局有效；永久奖励继续使用金币、零件和外观。生存状态从 `game.ts` 提取为独立模块。

## 9. 方案 C：纹章与朋友社区

### 9.1 纹章工坊

第一版支持上传、裁剪、缩放、旋转、六种滤镜、六种遮罩/边框和属性主题边框。

客户端负责交互预览，服务端重新解码、移除元数据并输出 256、512 和 1024 尺寸 WebP。原始上传默认不长期保留。

3D 模型使用独立圆形纹章覆盖网格，不要求全部模型重做 UV。

纹章用于陀螺核心、头像、VS 页面、必杀切入、分享卡和作品封面，但不影响战斗数值。

### 9.2 朋友展厅

作品卡显示作者、纹章、陀螺预览、五层零件、主属性、共鸣、流派和生存纪录。

只支持收藏、复制配装、发起挑战和查看战报。复制配装不复制强化等级。

### 9.3 朋友动态

只记录击败 BOSS、刷新生存纪录、发布纹章、完成挑战和解锁稀有零件。普通改装和普通战斗不进入动态。

## 10. 音乐、背景和表现

- 统一门户使用原创能量束或机械舱动态背景。
- 定制器使用低强度背景，战斗期间避免额外背景渲染负担。
- 音乐状态包括菜单、配装、发射、正常战斗、低转速危险、必杀、生存高波次、胜利和失败。
- 音量分为主音量、音乐、音效和环境音。
- 低性能模式可关闭动态门户、降低粒子和 Bloom、限制像素比。
- 属性主色可轻微影响现有技能粒子，但不要求第一阶段重做技能。

## 12. 错误处理

### 12.1 元素与版本

- 未知属性或零件使构筑无效，不随机替换。
- 旧属性通过明确迁移表转换。
- 未知规则版本提示更新页面。
- 挑战版本不兼容时允许查看，但不计正式成绩。

### 12.2 挑战

- 结果按挑战 ID 和玩家 ID 幂等提交。
- 原配装修改不影响历史挑战。
- 损坏挑战链接返回门户。
- 已删除零件使用快照或将挑战标记为过期。

### 12.3 图片

- 客户端预检类型和大小，服务端再次解码验证。
- 服务端处理失败时不创建数据库记录。
- 文件写入成功但数据库失败时只删除该明确临时文件。
- 数据库记录存在但文件缺失时作品标记不可用，不影响其他作品。

## 13. 实施阶段和验收

### 阶段 0：基线与版本

- 固定当前构建、数据契约、服务端和页面检查。
- 保存战斗黄金样例。
- 定义目录、元素、战斗、挑战和存档版本。

验收：未改变现有数值，测试全部通过。

### 阶段 1：共享七属性核心

- 增加属性数据、克制、共鸣、迁移和纯函数测试。

验收：49 种属性关系和所有五层分布均有确定结果。

### 阶段 2：定制器元素体验

- 增加属性徽章、共鸣盘、替换差异、流派和规则校验。

验收：定制器与共享计算完全一致，旧链接可迁移。

### 阶段 3：战斗元素接入

- 接入元素伤害、协调稳定、HUD、日志和结算解释。

验收：操作不变；克制影响受控；两类共鸣互斥。

### 阶段 4：邀请身份与 SQLite

- 增加 HTTP API、邀请码、本地身份、数据库迁移、进度首次上传，以及数据库和上传目录的基础备份/恢复脚本。

验收：无邀请码不能进入；重启后数据存在；迁移不重复奖励；空数据库可由一次测试备份恢复。

### 阶段 5：确定性异步挑战

- 迁移结果随机数、创建挑战、收件箱、回挑战和幂等结果。

验收：相同输入与种子得到相同结果。

### 阶段 6：八名对手战役

- 数据化对手、星级、奖励和服务器进度。

验收：完整通关；首次奖励不重复；无对手专用战斗副本。

### 阶段 7：完整生存模式

- 波次、精英、BOSS、局内奖励、倍率和成绩摘要。

验收：前五波曲线完整；奖励只在本局生效；测试种子可复现。

### 阶段 8：纹章工坊

- 编辑器、标准化图片、3D 覆盖网格和作品上限。

验收：定制器与 Arena 显示一致，失败上传不留孤立记录。

### 阶段 9：朋友展厅

- 作品列表、详情、收藏、复制、挑战和活动流。

验收：仅受邀玩家可访问；删除作品不破坏历史战报。

### 阶段 10：实时好友整合

- WebSocket 身份、公平/全力规则和版本校验。

验收：未认证连接不可加入；断线不会重复结算。

### 阶段 11：背景、音乐和体验打磨

- 动态背景、音乐状态、音量分类和低性能模式。

验收：无音乐重叠和 AudioNode 泄漏，低性能模式不改变逻辑。

### 阶段 12：服务端 AI 纹章

- 服务端代理、配额、超时和现有编辑器承接 AI 输出。

验收：前端无 API Key；AI 失败不影响本地纹章功能。

### 阶段 13：公网交付和运维

- HTTPS、SQLite WAL、将阶段 4 的基础备份升级为每日自动备份、健康检查、日志和管理员脚本。

验收：空目录可从备份恢复；日志不记录明文令牌或密钥。

## 14. 测试策略

### 14.1 单元测试

- 七属性关系和所有共鸣分布。
- 伤害拆分和协调倍率。
- 构筑流派和规则校验。

- 高波次限制敌人和粒子上限。

## 15. 主要风险

1. 异步挑战依赖确定性随机数迁移，不能提前实施。
2. 稀有度、强化、元素和克制叠加可能失控，因此公平模式必须使用基础属性。
3. `src/app/game.ts` 已过大，新模式必须进入独立模块，但不进行无关全面重构。
4. SQLite 与图片同机存储要求在开放纹章前完成基础备份和恢复演练，阶段 13 再完成自动化与运维加固。
5. 系统较多，入口必须按进度逐步开放。
6. AI 纹章是后置增强，不能阻塞核心循环。

## 16. 里程碑

| 里程碑 | 阶段 | 可玩成果 |
|---|---|---|
| M1 元素改装实验室 | 0–3 | 七属性装配和战斗生效 |
| M2 朋友挑战版 | 4–5 | 邀请进入、异步挑战和回挑战 |
| M3 单人完整版 | 6–7 | 八名对手和完整生存 |
| M4 创作社区版 | 8–9 | 纹章工坊和朋友展厅 |
| M5 联机与视听版 | 10–11 | 公平实时战斗和动态音画 |
| M6 AI 与稳定版 | 12–13 | AI 纹章、公网备份和完整验收 |

关键依赖链为：

```text
共享元素规则 → 定制器解释 → 战斗接入 → 确定性随机 → 好友挑战
```

每个里程碑都必须形成可独立游玩的版本，并通过该阶段验收后再进入下一阶段。
