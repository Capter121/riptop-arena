# NSS Arena 阶段 5B：异步好友装配幽灵挑战设计

日期：2026-08-10
状态：设计已逐节批准，等待书面规格复核

## 1. 背景

阶段 5A 已经建立版本化种子、确定性随机流、固定 60Hz 战斗步进、语义化输入日志、规范化战果摘要以及双浏览器一致性验证。当前项目也已经具备邀请码身份、浏览器本地身份保存、服务端 progression 同步、NSS 五件装配和现有 `challenges` 数据表。

阶段 5B 在这些能力之上增加仅供受邀朋友使用的异步挑战。创建者分享邀请链接；另一名玩家主动认领后，使用自己的 NSS 装配对战由确定性 AI 控制的创建者装配幽灵。它不是实时联机，也不改变现有博弈战斗、属性克制、共鸣、流派、QTE、物理或胜负规则。

## 2. 目标

1. 允许玩家从门户使用服务端已同步的最新 NSS 五件装配创建挑战链接。
2. 未定向邀请由第一名主动点击“认领并应战”的其他玩家获得；仅打开链接不绑定身份。
3. 认领时冻结双方装配和规则输入，之后的装配或升级变更不影响该场挑战。
4. Arena 使用应战者作为玩家、创建者装配幽灵作为确定性 AI 敌人，沿用现有完整战斗模式。
5. 每条正式挑战只接受一个最终结果，并支持浏览器崩溃、刷新、断网和响应丢失后的安全重试。
6. 提供“等待我”“等待朋友”“历史战报”三个分组的单页挑战中心。
7. 允许已完成挑战的应战者创建一条角色互换、定向给原创建者的新回挑战。
8. 保持既有单人模式、属性系统、确定性回放、progression 和备份恢复兼容。

## 3. 非目标

阶段 5B 不包含：

- 实时 P2P 或服务器权威联机。
- WebSocket、推送通知、好友列表或在线状态。
- 服务端 Three.js、无界面物理演算或强反作弊。
- 公开挑战广场、公开排行榜或陌生人匹配。
- 玩家可见的逐回合回放播放器。
- 挑战金币、经验、掉落、解锁或生涯进度奖励。
- 一条挑战多次结算或三局两胜。
- 保存多套装配收藏。
- 纹章、头像生成或服务端 AI 图片生成。
- 修改七属性、属性克制、共鸣、流派加成或战斗平衡。

## 4. 已批准的产品规则

### 4.1 身份与入口

- 站点继续通过邀请码进入。
- 玩家只填写昵称；`playerId` 和 `deviceToken` 继续由浏览器本地保存。
- 所有挑战 API 复用 `Authorization: Bearer <deviceToken>` 与 `X-Player-Id`。
- 邀请链接格式为 `/challenge/<offerId>`，由统一门户处理并保留原始路径。
- 未登录访问邀请链接时先进入现有邀请身份门；身份建立后自动回到原挑战。

### 4.2 创建与认领

- 创建入口位于门户，直接读取服务端同步的当前最新 NSS 五件装配。
- 没有服务端 NSS 装配时，不允许创建，并引导前往装配器。
- 创建表单只包含规则模式、竞技场和可选留言。
- 未定向邀请只有在其他玩家点击“认领并应战”时才绑定。
- 创建者打开自己的链接只能查看、复制链接或撤销，不能自我认领。
- 玩家可以在认领前进入装配器；装配器使用 `returnTo=/challenge/<offerId>` 返回原邀请。
- 同时认领时只有数据库事务中的第一名成功。

### 4.3 有效期与保留

- 未认领邀请自服务端创建时间起 24 小时有效。
- 判断边界为 `now < expires_at` 可认领，`now >= expires_at` 已过期。
- 已认领的正式挑战和已完成结果永久保留，除非未来另行批准数据清理方案。
- 创建者可以撤销仍处于开放状态的邀请；已认领邀请不能撤销。
- 过期是依据服务端时间推导的只读状态，不需要后台定时任务修改数据库。

### 4.4 规则模式

创建者可选择：

- `fair`：默认模式。保留零件、附加属性、属性克制、共鸣和流派；忽略双方所有会永久增强战斗能力的系统升级与零件升级。
- `full_power`：创建时冻结创建者当前升级，认领时冻结应战者当前升级。

两种模式都不改变原始存档，只改变该挑战不可变输入中的有效升级快照。

### 4.5 单次结果与回挑战

- 进入 Arena 或开始战斗不会消耗挑战机会。
- 浏览器崩溃、刷新或提交失败后可以从头重新打该场挑战。
- 服务端只接受第一份合法完成结果。
- 相同提交可以幂等重试；已完成结果不能覆盖。
- 再战必须创建新记录。
- 只有上一场的应战者能发起回挑战。
- 回挑战中，上一场应战者成为新创建者和装配幽灵；上一场创建者成为唯一目标应战者。
- 回挑战也是 24 小时有效的新邀请，使用新种子，并通过 `parentChallengeId` 形成历史链。

## 5. 数据模型

不得修改既有 `002_builds_and_challenges.sql`。新增增量迁移 `004_challenge_offers.sql`。

### 5.1 `challenge_offers`

新增邀请表：

| 字段 | 约束与语义 |
| --- | --- |
| `id` | UUID 主键 |
| `creator_player_id` | 创建者，外键到 `players` |
| `target_player_id` | 可空；回挑战时为唯一目标 |
| `parent_challenge_id` | 可空；回挑战来源 |
| `creation_request_id` | 创建幂等 UUID |
| `status` | `open`、`claimed` 或 `revoked` |
| `offer_json` | 规范化、不可变邀请快照 |
| `expires_at` | 服务端生成的 UTC 时间 |
| `claimed_challenge_id` | 可空；认领后关联正式挑战 |
| `created_at` | UTC 创建时间 |
| `updated_at` | UTC 更新时间 |

索引与唯一性：

- `(creator_player_id, creation_request_id)` 唯一，保证创建重试。
- `claimed_challenge_id` 唯一且可空。
- `(target_player_id, status, updated_at, id)` 支持“等待我”。
- `(creator_player_id, status, updated_at, id)` 支持“等待朋友”。
- `parent_challenge_id` 唯一且可空，保证同一来源挑战只生成一条回挑战。

### 5.2 扩展既有 `challenges`

通过 `ALTER TABLE` 和唯一索引新增：

- `offer_id`：来源邀请，唯一且允许旧行为空。
- `parent_challenge_id`：回挑战来源，允许为空。
- `result_submission_id`：首次结果提交 UUID，唯一且允许为空。

既有 `creator_player_id`、`recipient_player_id`、`status`、`input_json`、`result_json`、时间字段继续使用。旧数据无需回填，读取时按旧记录兼容处理。

### 5.3 邀请快照 `offer_json`

邀请快照至少包含：

- `challengeSchemaVersion`
- `catalogVersion` 与 catalog SHA-256
- `affinityRulesVersion`
- `battleRulesVersion`
- `simulationVersion`
- 服务端生成的确定性战斗种子
- 创建者 ID、创建时昵称和 NSS V2 装配
- `fair` 或 `full_power`
- 全力模式下创建者当前有效升级快照
- 竞技场 ID
- 当前确定性 AI 配置 ID
- 最多 120 字符的纯文本留言

不保存客户端提交的属性档案、共鸣、流派或最终统计值。这些派生值由权威装配数据和现有规则计算。

### 5.4 正式挑战 `input_json`

认领事务生成不可变正式输入：

- 复制邀请中的版本、种子、规则、竞技场和创建者快照。
- 增加应战者 ID、认领时昵称和服务端同步的 NSS V2 装配。
- 全力模式增加应战者认领时有效升级快照。
- 固定角色：应战者是 `player`，创建者装配幽灵是 `enemy`。
- 保存来源 `offerId` 和可选 `parentChallengeId`。

正式输入生成后不能更新。昵称快照用于历史展示；玩家以后改昵称不改写战报。

## 6. 状态机与原子性

```text
offer open
  -> claimed -> challenge pending -> challenge completed
  -> revoked
  -> expired（由 open + 服务端时间推导）
```

### 6.1 原子认领

认领在单个 `BEGIN IMMEDIATE` 事务中完成：

1. 读取邀请并检查创建者、目标、状态和有效期。
2. 拒绝创建者自我认领。
3. 读取并规范化应战者服务端 progression。
4. 校验双方装配和全部共享版本仍受当前客户端支持。
5. 构造不可变 `input_json`。
6. 插入一条 `pending` 正式挑战。
7. 条件更新邀请为 `claimed` 并写入 `claimed_challenge_id`。
8. 提交事务。

任何一步失败都回滚。并发失败者返回 `OFFER_ALREADY_CLAIMED`，不得产生孤立挑战。

### 6.2 结果状态

- `pending`：应战者尚未提交合法最终结果。
- `completed`：已保存唯一结果和完成时间。
- 开始、退出、刷新、离线和客户端本地失败不改变服务端 `pending`。
- 只有成功写入首次合法结果的事务把挑战改为 `completed`。

## 7. HTTP API

所有请求和响应使用 JSON，同源部署，复用现有身份中间件和错误响应格式。

### 7.1 创建邀请

`POST /api/challenge-offers`

请求：

```json
{
  "requestId": "uuid-v4",
  "mode": "fair",
  "arena": "arena-id",
  "message": "可选留言"
}
```

服务端读取创建者已同步 progression，不接受请求携带装配、升级或种子。相同创建者、相同 `requestId`、相同规范化内容返回原邀请；同 ID 不同内容返回 `IDEMPOTENCY_MISMATCH`。

### 7.2 查看邀请

`GET /api/challenge-offers/:id`

返回展示所需的最小数据、当前派生状态以及当前身份可执行动作。开放的普通邀请可由任一已认证受邀玩家查看；定向回挑战仅创建者和目标可查看。

### 7.3 认领邀请

`POST /api/challenge-offers/:id/claim`

无需携带装配。服务端读取认领者最新同步 progression，成功后返回正式 `challengeId` 和 Arena URL。

### 7.4 撤销邀请

`POST /api/challenge-offers/:id/revoke`

仅创建者可撤销 `open` 且未过期邀请。重复撤销返回当前撤销状态；已认领返回冲突。

### 7.5 挑战中心

`GET /api/challenges?group=<group>&cursor=<cursor>&limit=<limit>`

分组：

- `waiting_me`：当前玩家可以认领的定向邀请，以及当前玩家已认领但尚未完成的正式挑战。
- `waiting_friend`：当前玩家创建、仍待朋友认领或已认领但尚未结算的挑战。
- `history`：当前玩家参与的已完成挑战。

规则：

- 默认 `limit=20`，最大 50。
- 按最近更新时间与 ID 稳定倒序。
- 游标是服务端生成的不透明 `updated_at + id` 编码，客户端不得解析。
- 响应包含该玩家 `waiting_me` 的 `pendingCount`，门户用它显示角标。
- 页面进入、手动刷新或动作成功后重新读取，不使用 WebSocket。

### 7.6 挑战详情

`GET /api/challenges/:id`

仅参与者可读取。返回不可变输入、状态、允许动作和可选结果；不返回设备令牌或无关 progression 数据。

### 7.7 提交结果

`POST /api/challenges/:id/results`

请求：

```json
{
  "submissionId": "uuid-v4",
  "inputLog": {},
  "outcome": {}
}
```

仅正式挑战的应战者可以提交。服务端严格校验契约并在事务中写入第一份合法结果。

- 同一 `submissionId` 和同一规范化内容：返回已保存结果。
- 同一 `submissionId` 但内容不同：`IDEMPOTENCY_MISMATCH`。
- 不同提交写入已完成挑战：`CHALLENGE_ALREADY_COMPLETED`。

### 7.8 创建回挑战

`POST /api/challenges/:id/rematch`

仅已完成挑战的原应战者可以调用。服务器创建目标为原创建者的新邀请、生成新种子并关联 `parentChallengeId`。对同一父挑战重复调用返回同一回挑战邀请。

## 8. 客户端与 Arena 流程

### 8.1 模块边界

- `src/challenges/challengeClient.ts`：仅负责 HTTP 请求、响应解析和错误映射。
- `src/challenges/pendingChallengeResult.ts`：仅负责与本地身份绑定的待提交结果存储。
- 门户挑战页面：展示邀请、认领、撤销、分享和三个挑战中心分组。
- Arena：加载不可变挑战输入、运行战斗、冻结结果并触发提交。
- `server/challenges/challenge-service.mjs`：拥有全部创建、认领、列表、结算和回挑战业务规则。
- `server/http-server.mjs`：只做路由、身份调用、请求体上限和错误映射，保持薄层。

### 8.2 邀请页面

- 创建者：显示自己的装配、规则、竞技场、有效期、复制链接和撤销。
- 其他玩家：显示创建者装配、规则、竞技场、有效期、“调整我的装配”和“认领并应战”。
- 目标回挑战：只有指定目标看到认领入口。
- 已认领、过期、撤销、版本不支持和离线状态都有明确提示。

### 8.3 Arena 挑战模式

Arena URL 为 `/arena/?challenge=<challengeId>`，新增 `battleMode: 'challenge'`。

加载顺序：

1. 读取本地身份并请求正式挑战详情。
2. 校验挑战、规则、目录和模拟版本。
3. 用应战者不可变快照构建玩家。
4. 用创建者不可变快照构建 AI 敌人。
5. 使用服务端种子、竞技场和固定 AI 配置创建战斗上下文。
6. 复用发射、回合行动、属性克制、共鸣、流派、QTE、持续语音助威、固定 60Hz 和确定性 AI。

挑战模式不得：

- 发放或扣除金币。
- 更新关卡、生涯、解锁、升级或排行榜。
- 启动实时网络同步。
- 把视觉随机写入战斗结果。

### 8.4 结算与离线重试

战斗结束时：

1. 冻结 `BattleInputLogV1` 与 `BattleOutcomeSummaryV1`。
2. 生成一次 `submissionId`。
3. 在发送 HTTP 请求前写入浏览器本地待提交记录。
4. 调用结果接口。
5. 只有收到成功或确认相同提交已存在时才删除本地记录。

结算页显示胜负、结束类型、关键统计、规则模式、双方装配、返回挑战中心和可用的回挑战操作。提交失败时显示“重新提交”，不要求重新战斗。

挑战中心加载后，对当前身份的待提交记录自动尝试一次；同一页面会话不循环重试。不同身份不能读取或提交彼此的缓存结果。

## 9. 共享契约与服务端校验

### 9.1 权威边界

- 服务端是身份、邀请状态、有效期、种子、装配来源、升级快照和首次结果的权威。
- 客户端是实际战斗运行和最终结果的来源。
- 服务端严格验证结果结构，但不重新演算战斗。
- 客户端响应解析用于友好提示，不构成安全边界。

### 9.2 创建与认领校验

服务端必须校验：

- UUID、精确字段集合、字符串长度和枚举白名单。
- 服务端 progression 中存在 `latestNssLoadout`。
- NSS V2 接口、五个精确槽位、零件 ID 与槽位所属关系、五个属性值。
- 当前服务端支持的 catalog、属性、战斗、挑战和模拟版本。
- 竞技场与 AI 配置来自当前白名单。
- 全力模式升级值来自服务端规范化 progression；公平模式有效升级归零。

不得接受客户端提交的装配快照、升级、种子、派生属性档案、共鸣、流派或最终战斗统计作为邀请输入。

### 9.3 结果校验

请求体最大 2 MB。服务端对 `BattleInputLogV1` 和 `BattleOutcomeSummaryV1` 执行与客户端记录契约一致的严格校验：

- 字段集合精确，不接受额外字段。
- `simulationVersion` 受支持。
- 日志与摘要种子都等于挑战种子。
- 发射值有限且在当前合法范围。
- 回合从 1 连续递增，最多 256 个。
- `decisionTicks` 是当前范围内安全整数。
- 行动种类和技能 ID 在白名单中。
- QTE 分数是有限数值。
- 语音帧是 `0..255` 整数，最多 360,000 个。
- 语音帧数量等于摘要 `tickCount`。
- 日志回合数等于摘要 `turnCount`。
- 胜者、结束类型和最终陀螺状态字段有效。
- 所有最终数值有限，不接受 `NaN`、无穷或 JSON 之外的数值表示。

服务端不会证明 AI 行动、伤害过程或最终状态确实由日志演算得到。这是本阶段明确接受的信任边界。

### 9.4 规范化与幂等比较

服务端只保存按固定字段顺序重新构造的规范化 JSON，不直接保存客户端原始对象。幂等重试比较规范化后的语义内容；键顺序和无意义空白不同不构成冲突，值不同构成冲突。

`result_json` 保存规范化后的 `submissionId`、`inputLog` 和 `outcome`。因此首次写入后，服务端可以直接比较同一提交 ID 的规范化内容并返回原结果，不需要额外的推测性哈希字段。

## 10. 错误契约

除现有身份错误外，至少提供以下稳定错误码：

- `NSS_LOADOUT_REQUIRED`
- `CHALLENGE_VERSION_MISMATCH`
- `INVALID_CHALLENGE_REQUEST`
- `IDEMPOTENCY_MISMATCH`
- `OFFER_NOT_FOUND`
- `OFFER_FORBIDDEN`
- `OFFER_SELF_CLAIM_FORBIDDEN`
- `OFFER_ALREADY_CLAIMED`
- `OFFER_REVOKED`
- `OFFER_EXPIRED`
- `OFFER_TARGET_MISMATCH`
- `CHALLENGE_NOT_FOUND`
- `CHALLENGE_FORBIDDEN`
- `CHALLENGE_ALREADY_COMPLETED`
- `INVALID_CHALLENGE_RESULT`
- `REMATCH_NOT_ALLOWED`

客户端根据错误码显示可操作提示，不依赖英文错误消息判断逻辑。

## 11. 隐私与安全边界

- 邀请 URL 不是身份凭证，所有读取与写入仍要求有效本地身份。
- 所有 SQL 使用参数绑定。
- 留言只按纯文本展示，禁止 `innerHTML`。
- API 响应只返回挑战所需昵称和装配，不返回设备令牌、邀请码或无关存档。
- 不记录麦克风音频，只保存每个固定 tick 的量化音量字节。
- 不为这个私人 MVP 增加复杂分布式限流；使用身份授权、事务、请求体限制和数组上限控制实际风险。
- 严格契约不能阻止懂技术的受邀玩家伪造一份结构合法的胜利结果，产品界面不得宣称强反作弊。

## 12. 测试策略

### 12.1 迁移测试

- 空数据库执行 001 至 004。
- 当前 003 数据库升级到 004，旧 challenge 行仍可读取。
- 迁移失败完整回滚。
- 唯一索引覆盖创建幂等、单次认领、单次结果和单个父挑战回挑战。
- 现有备份、恢复和迁移版本校验包含新表与新列。

### 12.2 契约单元测试

- 合法公平和全力邀请、正式输入、战斗日志和结果 fixture。
- 缺字段、额外字段、错误类型、错误枚举、未知零件和槽位错配。
- 错误种子、错误版本、断裂回合、非法行动、非法技能和非有限数值。
- 语音帧、tick、回合与请求体边界。
- 客户端解析器与服务端验证器使用同一 fixture 语料，接受和拒绝结论一致。

### 12.3 服务测试

使用内存 SQLite 和可注入时钟覆盖：

- 创建成功、缺少 NSS 装配、创建幂等和幂等冲突。
- 普通邀请、目标邀请、自我认领、目标不符、撤销和过期。
- `expires_at` 前一瞬可认领，边界时刻起不可认领。
- 两个身份并发认领只有一条正式挑战。
- 公平模式有效升级归零，全力模式双方在不同时间冻结。
- 邀请和正式输入不可变。
- 结果首次成功、相同提交重试、不同结果覆盖失败。
- 未授权结果、错误种子、错误版本和超限日志。
- 回挑战角色互换、目标固定、新种子、父链和重复调用幂等。
- 三分组查询、稳定游标、最大 limit 和 `pendingCount`。

### 12.4 HTTP 集成测试

- 两个独立身份通过真实 HTTP 完成创建、查看、认领、详情和结算。
- Bearer 令牌与 `X-Player-Id` 不匹配。
- 错误内容类型、损坏 JSON、超大请求体和不存在资源。
- 业务错误到 HTTP 状态和稳定错误码的映射。

### 12.5 客户端测试

- 邀请路由在身份门后恢复。
- 装配器 `returnTo` 往返。
- 不同邀请状态和动作权限。
- 三个挑战中心分组、加载更多和角标。
- 待提交结果先保存后发送、成功删除、失败保留、身份隔离和单次自动重试。
- 挑战模式不写入金币、解锁、关卡或升级。

### 12.6 浏览器端到端测试

使用两个独立浏览器上下文：

1. 创建者同步 NSS 装配并创建默认公平邀请。
2. 应战者打开链接，先查看但不绑定。
3. 应战者进入装配器修改并返回。
4. 应战者主动认领并进入 Arena。
5. 以 QA 加速路径完成一场确定性装配幽灵战并提交。
6. 创建者刷新挑战中心，在历史战报看到唯一结果。
7. 原应战者创建定向回挑战。
8. 原创建者认领回挑战。
9. 模拟首次结果响应丢失，刷新后幂等恢复成功。

最后执行现有单元测试、NSS 16 零件与 288 组合契约、构建、确定性双浏览器回放以及桌面和移动端回归。

## 13. 实施顺序

1. 为迁移和服务行为编写失败测试，再新增迁移 004。

4. 添加薄 HTTP 路由和双身份集成测试。
5. 实现客户端请求层、邀请页面和挑战中心。
6. 实现 Arena `challenge` 模式，保证不触碰现有战斗规则。
7. 实现本地待提交结果和离线幂等恢复。
8. 完成双浏览器 E2E、备份恢复验证和完整回归。

每一步只有在对应验证通过后才进入下一步；稳定步骤应独立提交。不得顺便重构视觉、音频、属性、装配、物理或实时联机代码。

## 14. 成功标准

- 已认证玩家可以用服务端最新 NSS 装配创建 24 小时邀请链接。
- 仅查看链接不认领；首次主动认领原子成功，其他并发认领者失败。
- 公平和全力模式按批准的时间点冻结正确输入。
- Arena 使用应战者装配对战创建者装配幽灵，并保持现有完整战斗体验。
- 相同挑战输入、种子和语义操作继续产生确定性结果。
- 每条正式挑战只能保存一个结果；相同提交可以安全重试且不能覆盖。
- 断网、刷新或响应丢失后，本地待提交结果可以恢复。
- 三个挑战中心分组、角标、分页和回挑战方向正确。
- 挑战不改变金币、升级、解锁、关卡或其他 progression。
- 数据库重启、备份和恢复后邀请、正式挑战、结果和父链保持完整。
- 现有战斗、属性、装配、progression、构建和浏览器回归全部通过。

## 15. 风险与限制

- 本方案信任受邀客户端的语义结果，无法阻止手工构造合法 JSON 伪造胜利。
- 服务器不保留旧模拟器实现时，未来规则升级可能只能展示旧战报，不能重新播放；本阶段没有玩家回放功能，因此不提前实现版本归档框架。
- 逐 tick 语音音量 JSON 比原始字节数组更大；阶段 5B 先用 2 MB 请求和 tick 上限控制范围，不提前引入压缩协议。
- 无 WebSocket 意味着挑战状态通过进入页面、手动刷新和动作后的重新读取更新，符合私人朋友场景。
- 已认领及已完成记录永久保留可能让数据库持续增长；当前使用规模很小，暂不加入清理和归档策略。
- 当前 NSS 合法性继续依据项目现有七属性契约和装配规则；如果后续收紧某个槽位可选属性，应单独升级共享规则版本，不能在挑战服务中暗自增加不同规则。
